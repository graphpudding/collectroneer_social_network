# ТЗ: каталог коллекционных объектов

Версия 2 · 2026-10-30 · основа: ТЗ v1 от @matthew

Что изменилось относительно v1: каталог теперь рассматривается как живая база продукта, на которую ссылаются коллекции пользователей. Добавлены разделы: реестр стабильных ID, слой экземпляров, правки пользователей, лицензии данных, кэш LLM, публикация в БД, изображения в продукте. Продукт англоязычный и международный.

---

## 1. Цель и устройство

Агент строит расширяемый конвейер, который собирает открытые каталоги коллекционных объектов в единую базу. Первая категория — плёночные фотокамеры. Цены не собираются.

Каталог — фундамент соцсети для коллекционеров: на записи каталога ссылаются коллекции пользователей, вишлисты и поиск владельцев. Поэтому:

- ID записей вечные: никогда не меняются, не переиспользуются и не удаляются (раздел 4);
- у каждого поля есть источник, включая правки пользователей (раздел 6);
- повторные прогоны конвейера не ломают то, на что уже ссылаются пользователи.

Устройство:

- **Ядро** (этот документ) — всё, что не зависит от категории: политика источников, общая схема, реестр ID, конвейер, правила качества, структура файлов, приёмка. Пишется один раз.
- **Модуль категории** — отдельный документ `categories/<category>/MODULE.md` и конфиг `config.yaml`: источники, scope, поля `attributes`, правила разбора и дедупа, приоритеты полей, пилот. Первый модуль — `film_cameras`.
- **Шаблон модуля** — бланк для новой категории (приложение A). Новая категория не должна требовать правок ядра. Если требует, ядро спроектировано неправильно, и агент сообщает об этом.

Язык продукта и каноничных названий — английский. Названия на других языках хранятся как метки и алиасы (раздел 3.2).

## 2. Политика источников и адаптеры

Берём только из открытого доступа и не нарушаем правила источника.

Источник допускается, если выполнено всё:

- данные открыты: публичный API, официальный дамп или открытая лицензия (CC0, CC BY, CC BY-SA и т.п.);
- условия использования и robots.txt не запрещают автоматический доступ;
- доступ не требует обхода капч, блокировок, лимитов или авторизации, которой у нас нет.

Источник, не проходящий эти условия (например, CollectiBlend), в конвейер не подключается. Допустимая альтернатива — запросить у владельца дамп или доступ. Такой источник подключается только по решению владельца проекта и с письменным разрешением в `docs/permissions/`.

**Новое: лицензия источника фиксируется в конфиге.** У каждого источника в `config.yaml` указаны `license` (например, `CC0`, `CC BY-SA 3.0`), `share_alike: true|false`, `attribution` (строка для указания авторства) и ссылка на страницу условий. Лицензия проверяется на этапе разведки, а не берётся из памяти.

Адаптеры — переиспользуемые модули ядра. Категория лишь выбирает их и задаёт параметры.

| Адаптер | Для чего | Первое применение |
|---|---|---|
| `wikidata_sparql` | SPARQL-запросы с пагинацией, метки на всех языках, свойства | Камеры |
| `mediawiki_api` | Категории, wikitext, ревизии, файлы и их лицензии на любой MediaWiki | Camera-wiki |
| `commons_imageinfo` | Лицензия и автор файла Wikimedia Commons | Фото из Wikidata |
| `rest_api` | Постраничный JSON API с ключом или без | Позже: pokemontcg.io, Numista |
| `dump_file` | Загрузка и разбор официальных дампов (CSV, XML, JSON) | Позже: Discogs, Rebrickable |
| `user_edits` | Одобренные правки пользователей, выгруженные из БД продукта (раздел 6) | Все категории |

Каждый адаптер сохраняет сырые ответы в `raw/` вместе с ID ревизии или датой ответа и поддерживает возобновление с места остановки.

## 3. Общая схема данных

Одна запись — одна модель или вариант модели, не экземпляр. Поля ядра одинаковы для всех категорий, всё специфичное лежит в `attributes`, схему которых задаёт модуль категории. Пустое поле остаётся пустым, без «unknown».

### 3.1 Поля ядра

| Поле | Тип | Пример (камера) | Правило |
|---|---|---|---|
| `id` | string | `film_cameras:000123` | Из реестра ID (раздел 4), префикс = категория. Вечный |
| `status` | enum | `active` | `active` / `merged` / `retired` (раздел 4) |
| `merged_into` | string | | ID записи, в которую влита эта, если `status = merged` |
| `category` | string | `film_cameras` | Ключ модуля категории |
| `name` | string | `FM2` | Каноничное название модели на английском (как в англоязычных источниках) |
| `maker` | string | `Nikon` | Производитель, художник, издатель, монетный двор — по смыслу категории. Нормализуется по словарю алиасов |
| `labels` | object | `{"ru": "Зенит-Е", "ja": "…"}` | Названия на других языках из источников (метки Wikidata и т.п.) |
| `aliases` | string[] | `FM-2` | Варианты написания, рыночные и региональные имена, транслитерации (3.2) |
| `year_start` | int | 1982 | Начало выпуска / год создания |
| `year_end` | int | 2001 | Конец выпуска |
| `country` | string | `Japan` | Страна производства, если указана. Английское название |
| `production_count` | object | см. 3.3 | Тираж |
| `attributes` | object | `camera_type: SLR` | Поля категории по схеме модуля |
| `image_url` | string | URL | Одна основная картинка, прямая ссылка на источник |
| `image_license` | string | `CC BY-SA 4.0` | Обязательно, если есть `image_url` |
| `image_author` | string | | Автор файла |
| `external_ids` | object | `wikidata: Q…, camerawiki: Nikon_FM2` | ID во всех источниках |
| `source_urls` | string[] | | Все страницы, откуда взяты данные |
| `field_sources` | object | `year_start: wikidata` | Источник каждого заполненного поля, включая поля `attributes`. Значения: ключ источника, `<source>_llm`, `user_edit:<edit_id>` |
| `data_license` | string | `CC BY-SA 3.0` | Самая строгая лицензия среди источников, давших поля записи (раздел 7) |
| `attribution` | string[] | | Строки указания авторства для источников записи |
| `match_confidence` | enum | `high` | `high` / `medium` / `low` для сведённых записей |
| `notes` | string | | Конфликты значений, сомнения |

### 3.2 Названия, алиасы, поиск

Продукт международный, поэтому найти вещь должно получаться под любым её именем:

- `name` — каноничное английское название без имени производителя (`FM2`, а не `Nikon FM2`). Полное отображаемое имя = `maker` + `name`.
- `labels` — названия на других языках как есть: кириллица, японский, немецкий и т.д.
- `aliases` — всё остальное, под чем вещь ищут: написания с дефисом и без (`FM-2`), региональные рыночные имена (одна модель под разными названиями на разных рынках), исторические имена производителя (`Asahi Pentax` → `Pentax`), латинские транслитерации (`Zorki` / `Zorkiy` / `Zorky`).
- Ключ поиска и дедупа строится из `name`, `labels` и `aliases`: Unicode NFKC, casefold, снятие диакритики, удаление пробелов, дефисов и точек, отбрасывание ведущего имени производителя.

Разные рыночные имена одной модели — это алиасы одной записи, если модуль не считает их отдельными вариантами.

### 3.3 Тираж (`production_count`)

Объект, потому что точные цифры редки:

- `value` — число, если указано точно;
- `min` / `max` — если дан диапазон или «около N»;
- `basis` — `stated` (прямо указано), `serial_range` (оценка по диапазону серийных номеров), `estimate` (оценка из текста, «несколько тысяч»);
- `source` — ссылка и короткая цитата-обоснование.

Если тиража в источниках нет, поле пустое. Оценки «из общих знаний» запрещены.

### 3.4 Связи (`relations`)

Отдельная таблица `from_id · relation · to_id · source`: «объектив подходит к камере», «карта входит в сет», «модель — вариант другой модели». В первой итерации заполняется только `variant_of` (например, FM2n → FM2). Остальные типы заложены на будущее.

Приоритет источников при конфликте значений задаёт модуль категории по каждому полю. Конфликт фиксируется в `notes`.

## 4. Реестр стабильных ID

На записи каталога ссылаются коллекции пользователей, поэтому ID выдаётся один раз и навсегда.

**Хранение.** `categories/<category>/id_registry.csv`, лежит в git. Колонки: `id`, `status`, `merged_into`, `match_keys` (все `external_ids` в виде `source:value` через `|`), `first_seen_run`, `last_seen_run`. После запуска БД продукта мастер-копией становится таблица реестра в БД, а конвейер перед прогоном выгружает её в этот файл и после прогона загружает обратно.

**Присвоение ID на этапе сборки:**

1. Если хотя бы один `external_id` собранной записи есть в `match_keys` реестра — берётся этот ID, а `match_keys` пополняется новыми ключами.
2. Если ключи записи указывают на два разных ID — запись не собирается автоматически, а идёт в `review/id_conflicts.csv` как кандидат на слияние.
3. Иначе выдаётся следующий свободный номер. Номера не переиспользуются, даже освободившиеся.

**Жизненный цикл:**

- **Слияние дублей.** Одна запись остаётся `active`, другая получает `status = merged` и `merged_into`. Приложение переводит ссылки пользователей на итоговую запись. Слияние делается только через review, не автоматически.
- **Запись пропала из источников** (страницу удалили или переименовали). Запись не удаляется: она остаётся в каталоге с прежними данными, `last_seen_run` перестаёт обновляться, а REPORT.md перечисляет такие записи в разделе «осиротевшие».
- **`retired`** — только ручное решение для записей, признанных ошибочными (вне scope, мусор). Ссылки пользователей на них сохраняются, в поиске они не показываются.

Записи, созданные пользователями (раздел 6), получают ID из того же реестра.

## 5. Слой экземпляров (контракт с приложением)

Конвейер экземпляры не создаёт, но схема каталога должна их поддерживать. Уровни:

1. **Модель** — запись каталога (`Nikon FM2`).
2. **Вариант** — тоже запись каталога, со связью `variant_of` (`Nikon FM2n`, при необходимости `Nikon FM2n Black`). Что считать отдельным вариантом, решает модуль категории.
3. **Экземпляр** — вещь конкретного пользователя, живёт в БД приложения.

Минимальная схема экземпляра, на которую ориентируется каталог:

| Поле | Смысл |
|---|---|
| `item_id` | ID экземпляра |
| `owner_id` | Пользователь |
| `catalog_id` | Модель или вариант. Можно указать модель, если вариант неизвестен |
| `list` | `owned` / `wanted` (вишлист) / `for_sale` / `for_trade` / `sold` |
| `serial_number` | Серийный номер, если пользователь его указал |
| `condition` | Перечисление состояний, своё для каждой категории (задаёт модуль) |
| `photos` | Фото пользователя |
| `visibility` | `public` / `followers` / `private` |
| `notes` | Свободный текст |

Требования к каталогу, которые отсюда следуют:

- модуль категории может объявить в `attributes` перечисление `condition` и, если в источниках есть такие данные, `serial_ranges` — диапазоны серийных номеров по годам и вариантам. Это позволит определять год и вариант экземпляра по серийнику;
- поиск владельцев работает по `catalog_id` с учётом связей: в выдаче по модели показываются и владельцы её вариантов.

## 6. Правки пользователей

Открытые источники не покроют всё, особенно редкие модели и региональные выпуски, поэтому пользователи будут дополнять каталог.

- **Виды правок:** исправить поле существующей записи, добавить алиас или фото, предложить новую запись, предложить слияние дублей.
- **Модерация.** Правка живёт в БД продукта со статусом `proposed` → `approved` / `rejected`. В каталог попадают только `approved`.
- **Источник `user_edit`.** Перед прогоном конвейер выгружает одобренные правки в `categories/<category>/user_edits.jsonl` через адаптер `user_edits`. Каждое значение получает `field_sources = user_edit:<edit_id>`. Повторный прогон обязан воспроизводить правки, а не затирать их.
- **Приоритет.** По умолчанию одобренная правка пользователя важнее любого автоматического источника: это сознательное исправление. Модуль может это переопределить для отдельных полей. Если источник позже стал расходиться с правкой, это конфликт: он пишется в `notes` и в `review/user_edit_conflicts.csv`.
- **Новые записи от пользователей** проходят те же этапы нормализации, дедупа и валидации. У них может не быть `external_ids` — это допустимо, если в `field_sources` есть `user_edit`.
- **Фото от пользователей** для каталожной карточки допускаются, только если автор явно выбрал свободную лицензию при загрузке.

## 7. Лицензии данных

Лицензия касается не только фото, но и текста и данных, взятых из источника.

- Лицензия каждого источника записана в конфиге (раздел 2). Через `field_sources` у каждого поля известен источник, а значит, и лицензия.
- `data_license` записи — самая строгая лицензия среди источников её полей. `attribution` — список строк указания авторства этих источников.
- ShareAlike (CC BY-SA и т.п.) может распространяться на собранную базу. Как продукт будет это соблюдать (указание авторства в карточке, публикация части каталога под той же лицензией, отказ от отдельных полей из SA-источника), решает владелец проекта. Решение фиксируется в `docs/licensing.md` до запуска продукта.
- REPORT.md показывает распределение записей и полей по лицензиям.
- Агент не делает юридических выводов, а только собирает факты: лицензия, ссылка на условия, какие поля откуда пришли.

## 8. Конвейер этапов

Этапы одинаковы для любой категории. Модуль категории только параметризует их через `categories/<category>/config.yaml`. Запуск — одна команда с ключом категории, например `run --category film_cameras`. Можно запустить отдельные этапы: `--stage parse` и т.п.

1. **Разведка.** Для каждого источника модуля: найти нужные классы, свойства, категории, шаблоны. ID классов и свойств (QID/PID) не брать из памяти, а находить запросами и сверять по меткам. Проверить лицензию и условия использования. Оценить объём и время выкачки.
2. **Выкачка.** Адаптеры забирают данные в `raw/<source>/`. Сырые ответы сохраняются до любой обработки, с ID ревизии страницы. Повторный разбор не требует повторной выкачки. Инкрементальная выкачка: страницы с неизменившейся ревизией не перекачиваются.
3. **Фильтр scope.** Правила «входит / не входит» берутся из модуля. Спорное — в `review/scope_unsure.csv`, отсеянное — в `review/excluded.csv` с причиной.
4. **Разбор.** Сначала детерминированно (структурированные поля, инфобоксы, категории). Только для полей, которые так не нашлись, — извлечение LLM-ом из текста конкретной страницы: строгий JSON, цитата-обоснование, источник поля помечается `<source>_llm`. Результаты LLM кэшируются (раздел 9).
5. **Нормализация.** Словарь алиасов `maker`, ключ поиска (3.2), единицы и перечисления по схеме модуля, названия стран на английском.
6. **Сопоставление и дедуп.**
   - Явные перекрёстные ссылки между источниками важнее любой эвристики.
   - Точное совпадение ключа + `maker` → `high`. Ключ совпал, но год расходится больше чем на 2 → `medium`. Нечёткое совпадение (fuzzy ≥ 0.9) при совпадении `maker` → `low` и в `review/matches_to_check.csv`.
   - Варианты не склеиваются: правила «что считается отдельной моделью» задаёт модуль, связь пишется в `relations` как `variant_of`.
7. **Сборка.** Слияние полей по приоритетам модуля, с учётом правок пользователей (раздел 6). Присвоение `id` через реестр (раздел 4). Расчёт `data_license` и `attribution`. Выбор основной картинки: свободная лицензия, фото самого объекта.
8. **Проверка и отчёт.** Валидация по схеме, ручная выборка, `REPORT.md`, `diff.md` относительно прошлого прогона (добавлено, изменено, осиротело, слито).
9. **Публикация.** Загрузка в БД продукта (PostgreSQL): upsert по `id`, без удалений, в одной транзакции на категорию. Обновление реестра ID в БД. Поисковые индексы по ключу поиска, `labels` и `aliases` (триграммы). До появления БД этап только готовит `catalog.json` и SQL-миграцию.

Новая категория = новый конфиг + при необходимости новый адаптер в ядре. Код этапов 1–9 не меняется.

## 9. Правила доступа, качества и логирования

Данные не выдумываются: поле без подтверждения в источнике остаётся пустым.

**Доступ**

- Осмысленный User-Agent с контактом, например `CollectiblesCatalog/0.1 (contact@…)`.
- Запросы к одному источнику идут последовательно. Скорость задаётся в конфиге, по умолчанию не чаще 1 запроса в 2 секунды. Лучше собирать каталог несколько дней, чем получить бан. При 429/503 — ждать `Retry-After`.
- Для MediaWiki — пакеты до 50 заголовков и `maxlag=5`.
- Изображения конвейер не скачивает: в базу идут только URL, лицензия и автор.

**Качество**

- LLM-извлечение только из текста конкретной страницы, без знаний из памяти. Каждое такое значение логируется с цитатой.
- Валидация по схеме ядра и схеме `attributes` модуля. Годы вне допустимого диапазона категории и `year_end < year_start` — в `review/`.
- Перед сборкой — ручная проверка 30 случайных записей против исходных страниц.

**Кэш LLM и воспроизводимость**

- Каждое LLM-извлечение кэшируется по ключу `(source, page_id, revision_id, field, prompt_version, model)` в `categories/<category>/llm_cache.jsonl`. Кэш лежит в git.
- При повторном разборе значение берётся из кэша. LLM вызывается заново, только если изменилась ревизия страницы, версия промпта или модель.
- Благодаря кэшу повторный запуск на сохранённых `raw/` даёт идентичный результат.

**Логирование**

- `logs/run.log` — этапы, число запросов, ошибки, повторы.
- `logs/llm_extractions.jsonl` — страница, ревизия, поле, значение, цитата, попадание в кэш или новый вызов.
- Ни одна запись не исчезает молча: всё отсеянное — в `review/excluded.csv` с причиной, всё исчезнувшее из источников — в разделе «осиротевшие» отчёта.

## 10. Изображения в продукте

Конвейер хранит только ссылку, лицензию и автора. Массово показывать в продукте фото по прямым ссылкам на Wikimedia Commons и другие источники нельзя: это нагрузка на чужие серверы и зависимость от их доступности. Поэтому приложение держит собственный кэш превью (CDN), заполняемый из `image_url` с соблюдением лицензии. Автор и лицензия показываются в карточке. Это задача приложения, а не конвейера, но поля `image_license` и `image_author` обязательны именно ради неё.

## 11. Файлы, чекпоинты и приёмка

**Структура проекта** (монорепозиторий: конвейер и приложение рядом)

- `pipeline/core/` — конвейер, адаптеры, общая схема, реестр ID, валидаторы.
- `pipeline/categories/<category>/` — `MODULE.md`, `config.yaml`, `attributes.schema.json`, словари алиасов, `id_registry.csv`, `llm_cache.jsonl`, `user_edits.jsonl`, `raw/`, `review/`, `logs/`, `catalog.csv`, `catalog.json`, `REPORT.md`, `diff.md`.
- `pipeline/output/` — `catalog_all.csv` / `catalog_all.json` и `relations.csv`, объединённая база по всем категориям (в CSV массивы через `|`, объекты — JSON-строкой).
- `db/migrations/` — `.sql` миграции, которые применяет `dbmate`. Это единственное место, где меняется схема БД. Схема общая для конвейера и приложения, но конвейер пишет только в таблицы `catalog_*`.
- `web/` — приложение.
- `docs/` — это ТЗ, план, `licensing.md`, `permissions/` (разрешения владельцев закрытых источников, если появятся).

В git лежат код, конфиги, реестр ID, кэш LLM, `review/`, отчёты. `raw/` в git не кладётся: он большой, но восстановим повторной выкачкой.

**Чекпоинты.** Для каждой категории агент останавливается на трёх чекпоинтах и ждёт подтверждения:

| Чекпоинт | Когда | Что показать |
|---|---|---|
| 1. Разведка | После этапа 1 | Найденные классы, свойства, категории с ID; объём и время выкачки; лицензии источников; проблемы с доступом |
| 2. Пилот | Пилотный поднабор из модуля, все этапы | Пилотная таблица, статистика сопоставления, 10 спорных случаев |
| 3. Финал | После этапа 8 | Файлы категории, `REPORT.md`, `diff.md` |

**REPORT.md** — число записей всего и по источникам; топ-20 `maker`; заполненность каждого поля в процентах (включая `production_count`, `labels`, `aliases` и поля `attributes`); доля записей с фото и со свободной лицензией фото; распределение по `data_license`; итоги ручной проверки; осиротевшие записи; известные пробелы.

**Критерии приёмки (для каждой категории)**

- [ ] Нет записей вне scope модуля и дублей (выборка 30 записей + проверочные запросы модуля).
- [ ] У каждой записи заполнены `name`, `maker` и хотя бы один ID в `external_ids` либо `user_edit` в `field_sources`.
- [ ] У каждой записи с `image_url` заполнена `image_license`.
- [ ] Каждое поле прослеживается до источника через `field_sources` и `source_urls`.
- [ ] У каждой записи заполнены `data_license` и `attribution`.
- [ ] Повторный запуск на сохранённых `raw/` и кэше LLM даёт идентичный `catalog.csv`.
- [ ] Повторный запуск не меняет и не удаляет ни одного ранее выданного ID.
- [ ] Одобренные правки пользователей переживают повторный прогон.
- [ ] Подключение категории не потребовало правок кода этапов ядра.

## Приложение A. Шаблон модуля категории

Заполняется в `categories/<category>/MODULE.md`, машиночитаемая часть — в `config.yaml`.

1. **Ключ категории и определение.** Что считается объектом каталога, одной фразой.
2. **Scope.** Что входит, что не входит, пограничные случаи и как их решать. Проверочные запросы (известные объекты, которые обязаны найтись; объекты, которых быть не должно).
3. **Источники.** Для каждого: адаптер, параметры, лицензия, `share_alike`, `attribution`, ссылка на условия, лимит скорости.
4. **Смысл полей ядра для категории.** Что такое `maker`, `year_start`, `production_count` для этих объектов.
5. **Схема `attributes`.** Поля, типы, перечисления, единицы, допустимые диапазоны. Перечисление `condition` для экземпляров. По возможности `serial_ranges`.
6. **Модель / вариант.** Правила, когда это отдельная запись с `variant_of`, а когда алиас.
7. **Правила разбора.** Инфобоксы и шаблоны, свойства, сопоставление полей источника полям схемы. Какие поля можно извлекать LLM-ом.
8. **Нормализация.** Словарь алиасов `maker`, правила ключа названия, специфичные для категории.
9. **Приоритеты источников** по каждому полю, включая положение `user_edit`.
10. **Пилот.** Поднабор (например, 2–3 производителя), на котором проходит чекпоинт 2.
